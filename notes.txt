    -> Static Code Analysis - SCA (White Box Testing - QA / DevSecOps)

        -> Static code analysis is the "process" of examining source code, 
        without executing it to find potential bugs, security vulnerabilities and 
        quality issues.

        -> Automated tools(like SonarQube) can scan the code against predefined rules 
        to identify problems early in the development cycle, 
        promoting better coding practices and security.


    -> Static code analysis can help identify various types of issues, including:

        Syntax errors and typos
        Unused variables and methods
        Code duplication
        Security vulnerabilities (e.g., SQL injection, cross-site scripting)
        Memory leaks and resource leaks
        Performance issues
        Conformance to coding standards and style guidelines (e.g., indentation, naming conventions)

    -> Docker Supports Following Network Driver, Each designed for 
    Specific Use Case 

        -> Host Network Driver  

        -> None Network Driver 

        -> Bridge Network Driver (***)

    
    -> Host Network Driver      

        -> The host network driver in Docker removes network isolation 
        between a container and its host, allowing the container to 
        share the host's networking namespace directly.

        -> The container does not get its own IP address; 
        instead, it uses the host's IP address.

        -> Port Conflicts: Because the container uses the host's ports, 
        you cannot run two containers that use the same port 
        (e.g., two Nginx instances on port 80) using the host driver.
    
    
    
    -> None Network Driver 

        -> The "none" driver provides complete network isolation by 
        disabling all networking for a container.

        -> The container cannot reach external networks, 
        and no external network can reach the container.

        -> Docker does not assign any IP address to containers using this driver.

            -> NOTE: Observations made from above command 

                - **`login-volume`**: This is the name of a Docker-managed volume. 
                If it doesn't already exist, Docker will create it automatically.
                
                - **`/usr/share/nginx/html`**: This is the directory inside the container 
                where the volume is mounted.

                **Effect:**  
                Any files placed in `login-volume` on the host 
                (or within the volume if managed by Docker) will appear inside the 
                container at `/usr/share/nginx/html`. 
                Conversely, files inside that container directory will be stored in the volume.

                **Purpose:**  
                This setup is typically used to persist website files 
                (like HTML, CSS, JavaScript) across container restarts, 
                or to serve custom static content with nginx.

                In summary, `-v login-volume:/usr/share/nginx/html` 
                links the named volume `login-volume` to the container's web root directory, 
                allowing persistent and shareable storage of website content.

    -> Kubernetes Components / Architecture

        -> https://miro.medium.com/v2/1*UUU4oblu-xDDoZAitaRz2g.jpeg

    
    -> Master Components

        -> API Server: 
            
            -> The API server acts as the brain of the Kubernetes cluster. 
            It provides a central point of communication for all the other components. 
            When you want to create, update, or delete something in the cluster, 
            you communicate with the API server.

        -> etcd: 
            
            -> Think of etcd as the memory of the Kubernetes cluster. 
            It stores the configuration data and the state of the entire cluster. 
            When any component wants to know the current state of the cluster, it asks etcd.

        -> Scheduler: 
            
            -> The Scheduler is like a matchmaker. 
            Its job is to decide which worker node should run each new app container/pod. 
            It considers factors like available resources, to make sure app containers/pods 
            are placed on suitable worker nodes.

        -> Controller: 

            -> The Controller Manager is like the supervisor of the cluster. 
            It continuously observes the state of the cluster through the API server. 
            If it detects that the actual state of the cluster doesn't match the desired state 
            (for example, if an app container/pod goes down), 
            it takes action to make the cluster converge to the desired state.


    -> Worker Components

        -> Kubelet: 

            -> The Kubelet is like the worker's Agent Software.  
            It runs on every worker node and is responsible for making sure 
            that the containers/pods assigned to its node are running and healthy. 
            It takes care of starting, stopping, and monitoring containers within the pods. 
            It updates the status back to Master.

        -> Docker: 

            -> The container runtime is the software that runs and manages containers.  
            The container runtime is responsible for pulling container images from a registry, 
            creating containers, and managing their life cycles.

        -> Kube Proxy: 

            -> The Kube Proxy is like the traffic cop of the worker nodes. 
            It manages the network connections and routing between the containers/pods and services 
            within the cluster. It ensures that network traffic is correctly directed to the 
            right destination.

    
    -> Workstation Components

        -> Kubectl 

            -> kubectl is the official command-line interface (CLI) used 
            to communicate with the Kubernetes API and manage your 
            cluster's control plane. It allows you to deploy applications.
